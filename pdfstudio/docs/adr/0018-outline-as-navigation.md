# ADR-0018：目录是导航结构——空小节靠折叠，不靠隐藏

## 状态

Accepted（2026-08-19）

## 背景

「从目录页生成目录」上线之后，决策者的评价是「能跑通但不够 useful」。查下来不是识别
不准，是**做出来的东西没地方用**。

两条独立的代码路径导致同一个结果：

- `groupClipsBySection` 只留有摘录的组（加上它们的祖先）。零摘录时 `kept` 为空，
  返回空数组。
- `ClipsPane` 在 `clips.length === 0` 时提前 return 空状态，根本走不到渲染分组那一步。

**于是：花六次模型调用生成的目录，在划下第一条摘录之前一个字都看不到。** 就算划了几
条，也只显示那几条所在的小节。

「空的小节不出现」是 ADR 之前就写在 `outline.ts` 里的决定，理由原话是「22 项目录配
3 条摘录，画出 19 个空标题只会让这一栏没法看」。

**那条推理对论文成立，对书不成立。** 实测的两组数字放一起就是全部理由：

| | 目录项 | 典型摘录数 | 藏掉空小节的后果 |
|---|---|---|---|
| Attention（15 页论文） | 22 | 3–10 | 少看 19 行，无所谓 |
| 分布式系统概念与设计（654 页） | 目录横跨 6 页，粗估两三百条 | 早期为 0 | **整本书没有目录** |

论文的目录是**装饰**——15 页，滚一下就到底了，导航价值近似为零。几百页的书里目录是
**唯一的导航手段**，而那正是决策者当初提这个功能的场景（「经典的中文技术书，比如
分布式系统设计、CSAPP 这些大黑书」）。

## 决策

**目录是这本书的导航结构，不是摘录的分组标题。**

1. **全部小节都显示**，不论有没有摘录。推翻「空的小节不出现」。
2. **密度问题交给折叠**，不交给隐藏。
3. 摘录仍然嵌在它所属的小节下面——**不另开页签**。决策者的原话是「目录是 clip 的
   高一级的管理形式」，那是一棵树的两层，不是两个并列的视图。
4. 带摘录的小节标数量，让「我在哪儿划过」一眼可见。

## 为什么折叠而不是隐藏

两者都能解决「一栏塞不下两三百行」，但**丢掉的东西不一样**：

- **隐藏**丢掉的是**存在性**：你不知道第 12 章存在，也就不会想到跳过去。而且丢得
  没有声音——界面看起来一切正常。
- **折叠**丢掉的只是**细节**：第 12 章始终在那儿，展开就有下一层。

一句话：**隐藏回答不了「这本书有什么」，折叠可以。** 而对一本 654 页的书，「这本书
有什么」正是打开它的第一个问题。

## 为什么不给目录单开一个页签

侧栏已经有「摘录 / 问文档」两个页签，加第三个是最省事的做法，但它把一棵树切成两半：
一边是小节标题，一边是挂在小节下的摘录，两边各滚各的。读者要回答「第 12 章我划过
什么」就得在两个页签之间来回对。

**一棵树就该长成一棵树。** 折叠之后密度问题已经解决，切开的理由就不存在了。

## 代价

1. **首屏默认折到几层，是个没有数据支撑的选择。** 目前定在「顶层展开、其余折起」。
   一本只有一层目录的书会显得没做折叠，一本五层的书顶层可能还是太多。这个数迟早要
   按真实的书调，而不是现在拍死。
2. **带摘录的小节要默认展开，于是「默认视图」不是纯粹的层级函数**，而依赖数据。
   代价是同一本书在划了摘录前后长得不一样——但那正是想要的。
3. **折叠状态不落盘。** 它是「此刻在找什么」，不是这本书的属性（同 `ClipsPane` 里
   筛选状态的口径）。代价是关掉再打开要重新展开。
4. **论文那一侧变差了一点。** 22 项目录配 3 条摘录，现在会看到 22 行而不是 3 行。
   接受：折叠之后它们不占地方，而多出来的是这篇论文的结构。

## 边界

- **不改 `Clip` 的契约。** 归属仍然是算出来的、不落盘（同 issue 01 的口径）。
- **不做跨书的目录。** 目录是一本书的属性。
- **小节标题进不进检索，不在这份 ADR 里定**——那是要 eval 说话的事（同 ADR-0017
  对标签名的处理）。
