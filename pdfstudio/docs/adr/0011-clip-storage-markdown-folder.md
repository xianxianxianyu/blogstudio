# ADR-0011：摘录存成 markdown 文件夹，数据库只当索引

## 状态

Accepted（2026-08-14）

## 背景

摘录要落盘，否则关掉应用就没了。候选是把它塞进 SQLite（正文文本 + 截图 BLOB），
还是一条摘录一个文件夹。

## 决策

**一条摘录 = 一个文件夹**：`<clip-id>/index.md` + `<clip-id>/.asset/`。
`index.md` 的正文是摘录本来就有的双语 markdown，结构化字段（状态、锚点、标签）放
frontmatter；截图与抠出的图放 `.asset/`。

**数据库只存索引**（id、docId、页码、状态之类），用来列出与检索。

**文件是唯一真相，数据库是可重建的缓存。** 索引坏了扫一遍文件夹就能重建；反过来不成立。

## 为什么

**markdown 不是为存储发明的格式，它本来就是这个领域里的形状。** `CONTEXT.md` 说摘录
「持有双语 markdown——逐字的原文、其译文、从区域抠出的图、以及作为地面真值的整块区域
截图」；`CONTEXT-MAP.md` 说摘录的 markdown 正文「直接映射到 Blog Studio 的 markdown
block（无需格式转换）」。存成 markdown 是**零转换**；存成 BLOB 反而要多一层编解码，
还让摘录变成不可读的二进制。

**截图存字节而不是重渲染。** `Clip` 同时持有 `anchor`（页码 + 矩形），理论上可以从原
PDF 重新渲染。但 `CONTEXT.md` 把 screenshot 定义为「作为**地面真值**的整块区域截图」
——重渲染的结果会随 pdf.js 版本与渲染参数变化，那就不是真值了。而且读者可能把 PDF
从书架删掉，摘录不该跟着失效。代价是存储膨胀（一条摘录几十 KB），可以接受。

**对 agent 友善是附带收益**：这个仓库本来就是 markdown 驱动的（`.scratch/` 的 issue、
所有设计文档），摘录落成同样的形状，读者可以 grep、可以 git、可以手改。

## 代价

1. **原子性**：写 markdown + 写 asset + 更新索引不是一个事务。做法是先写文件（临时目录
   再 `rename`，同一文件系统上原子），再更新索引；索引落后由重建修复。**顺序不能反**
   ——文件是真相，先落它。
2. **frontmatter 需要 schema 且要版本化**。这是**内部存储格式**，不是跨产品的传输格式，
   所以不与 `docs/adr/0001-shared-knowledge-base.md`「不引入需要版本化的传输格式」冲突
   ——那条讲的是两个产品之间的边界。
3. **文件可被手改，绕过 reducer 的不变量**（例如「原文只准修错字」）。对 local-first
   的个人工具这更像特性而非缺陷，但要写明：那条不变量只在应用内成立，直接编辑文件不受
   约束。读到手改过的文件时不做校验、不做修复，按现状加载。
4. 一条摘录一个文件夹，几千条就是几千个文件夹。桌面无碍；移动端与未来的同步服务器要
   注意，届时可考虑按文档分目录。

## 边界

- **不为知识库定存储格式。** 知识库是第三个系统，两个产品都不拥有它
  （`docs/adr/0001-shared-knowledge-base.md`）。PDF Studio 的职责到「交出一条 `Context`」
  为止，怎么存是它自己的事。而且 `Context` 全是文本字段、没有多模态资源，套这套
  「markdown + .asset」的结构对它是多余的。
- **`ClipStore` 与检索索引先分开存**，不预先合并。检索索引目前根本没落盘（每次会话在
  内存里重建），把一个还不存在的东西的存储需求塞进 `ClipStore` 的设计，正是 seam 纪律
  要删的 indirection。等索引真要持久化（ADR-0004 指向 SQLite FTS5）时再看要不要并库
  ——那时才有真实约束可依。
