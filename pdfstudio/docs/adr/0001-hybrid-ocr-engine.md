# 混合 OCR：文字区走文本层，图片区走视觉模型

一个被截取的区域按两条路之一做 OCR：文字区直接抽文本层（精确、免费、即时）；图片和公式区交给云端多模态模型，一次读图 + 翻译。我们否决了单一像素 OCR 管线，因为它对有文本层的 PDF 有损且慢；也否决了全本地 OCR，因为它处理公式和图文混排很差。公式区的 LaTeX 是公式的逐字无损编码，归入原文（sourceText）而非多模态描述——这样公式摘录才有 evidence、才能入库。具体的云端模型由 ADR-0005 选定（用户配置的 OpenAI 兼容端点，默认 GPT）。

## 修订（2026-08-14）：视觉路由改为本地 / 云端双引擎

**两条路由的结构不变**，改的只是视觉路由背后由谁来算：从「只有云端」改为**本地与云端双引擎，设置里由读者选**，并提供模型的一键下载。

**为什么改。** 原文否决全本地 OCR 的理由是「处理公式和图文混排很差」——那是针对传统像素 OCR 管线的判断。此后 VLM 形态的本地 OCR 成熟起来，这条否决的适用范围随之收窄：它仍然否决传统管线，但不再自动否决本地 VLM。ADR-0006 的 local-first 立场也指向同一边。

**这条修订不否定原判断，只是把它的适用面收窄，并给出一个可验证的门槛**（见下方验收标准）。

**架构影响很小，因为缝的位置本来就对。** `Recognizer` 只依赖 `model: ModelClient` 这个端口（ADR-0009），选本地还是云端 = 构造哪一个 `ModelClient`，是 `Config` 的事：

- 本地引擎若能暴露 **OpenAI 兼容接口**（经 vLLM / Ollama / llama.cpp 之类），它直接落在现有端口后面——`Recognizer`、`Chat`、现有 adapter **一行都不用改**，只是 `baseURL` 指向本机。ADR-0005 的「填成本机地址就是本地部署」本来就预留了这条路。
- 本地引擎若**不是**对话式模型（例如 Python 管线形态的 OCR），则要新开一个端口并新写 adapter，代价明显更高。

具体选哪个引擎见 `research-local-ocr-engine.md`，本 ADR 不预判。

**验收标准。** 任何本地引擎要成为默认之前，必须跑通与云端同一套 eval（`eval/run-recognizer.ts`，19 张标注样本），并达到可比的 `kind` 合规率与公式 LaTeX 质量。云端路线 2026-08-14 的实测是 19/19。**没有过这个门槛的引擎可以作为可选项提供，但不设为默认。**

**代价。** 新增两件此前没有的东西：模型权重的下载与本地管理（体积、校验、存放位置、许可证是否允许应用内分发），以及设置界面里的引擎切换。前者是新的关注点，落地形态取决于所选引擎，等 research 定了再写进 `architecture.md`。
