# ADR-0017：颜色即分类——色相归读者，浓淡归 important

## 状态

Accepted（2026-08-17）

## 背景

决策者要给高亮换颜色。追问一句「颜色只是视觉分组，还是要有含义」之后定的是**颜色即
标签**：可筛选、名字进检索。

问题在于**颜色这条通道已经被占用了**。ADR-0012 定的保留轴（`important`）在界面上就是
靠颜色深浅表达的：

    .mark.line       淡黄  随手划过的，第 7 天会被回收
    .mark.line.keep  浓琥珀 标了重要，永久保留、进 RAG

读者一旦能自选颜色，「这条会不会被删」就没有地方显示了。而那恰恰是最不该看不见的
一件事——回收是**破坏性**的。

## 决策

**两条轴拆开，各占一个视觉维度：**

- **色相由标签给**（五个预设槽位）
- **明度由 `important` 给**（34% → 55% alpha）

数据模型上也是两个字段：`Clip.tagId` 与 `Clip.important`。

## 为什么不合成一根轴

「把某个颜色定义为『重要』」看着能省一个字段，实际是把两个正交的问题绑死：

- 想留一段**存疑**的内容，就只能把它改成「重要色」，于是它在筛选里从「存疑」消失
- 反过来，标了「存疑」就等于放弃了「别删我」

这和 ADR-0012 当初拒绝拿 `promoted` 代替 `important` 是同一个错误的两种形态——那次是
「纯图永远进不了 promoted，合并成一根轴的话一张关键架构图必被回收」。

**标签说「这是什么」，☆ 说「别删」。** 两句话不互相蕴含。

## 为什么是五个预设，不是取色器

荧光笔本来就没有连续色域。更实际的理由：预设能保证每一种压着黑字都还读得清，而自由
取色一定会有人选到深蓝，然后整段字消失——而且是**自己造成的、看不出原因的**消失。

## 为什么标签是全局的，而摘录只存 id

「存疑」在这篇论文和那篇论文是同一件事：那是读者的习惯，不是某本书的属性。所以注册表
在书架根上（`<root>/tags.md`），一份。

摘录只存 `tagId`，名字不冗余进摘录文件——**改一次名不该重写几百个文件**。

这**不违反 ADR-0011**「文件是唯一真相」。那条针对的是摘录的**内容**（原文、译文、
笔记、截图）必须在索引丢失后还能重建；`tags.md` 自己也是磁盘上可读可手改的文件，
不是可重建的缓存。有一条测试直接钉住这个区别：改名之后摘录文件逐字节不变。

## 代价

1. **明度这条轴的分辨率很低。** 34% 与 55% 在浅色相（黄）上分得开，在深色相（紫）上
   差别更小。真不够用的话，出口是给 `important` 再加一条左边缘的实线，而不是把色相
   要回来。
2. **手改 `tags.md` 可能改出不认识的颜色。** 读的时候归一成固定顺序的五条，缺的补
   默认——手改一个字就让调色盘少一格的话，「文件可以手改」这句话就成了陷阱。
3. **标签名进不进检索还没定。** 见 ADR 末尾的边界。

## 边界

- **一条摘录一个标签。** 多标签要另一套 UI，而现在连一个都还没有。
- **不做标签的层级、不做跨书的标签统计。**
- **标签名是否进入检索文本，由 eval 决定，不在这份 ADR 里定。** `clip-chunks.ts` 有条
  反着的先例——文本路由的原文**故意不进索引**，因为重复内容会往背景分布掺水，而
  abstention 的门槛（`MIN_PEAK_MARGIN`）正是按背景分布标定出来的，刚从 0.10 重标到
  0.15。一个 2–4 字的名字附在**每一条**摘录块上有同样的风险。
