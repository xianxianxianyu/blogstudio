# ADR-0005：一份设置，四页——共用的是能力，各自的是各自的

## 状态

Accepted（2026-08-20）

## 背景

决策者报的现象是「Reader 的设置和 Context、Writer 的不互通」。

查下来，**「不互通」是个错觉**：三侧读的一直是同一个 `config.json`，从来没有过三份。
真正坏的是四件事，凑在一起看起来就像三份设置各走各的：

1. **`chat` 在用，设置里没有它。** `main.tsx` 拿 `endpoint("chat")` 给「问文档」建模型，
   而设置页的能力清单是手写的另一份，上面只有识别、翻译、检索向量。于是问文档永远只能
   跟随默认组，既不能单配，也不能自检。
2. **`embedding` 在设置里，却不接线。** 那三栏可填，接线那侧写死了本地 embeddinggemma
   （`createHttpEmbedder` 压根不读配置）。读者填进去的东西**无声失效**。`claim` 同理，
   从来没接过线。
3. **一个按钮，三种量程混在一张表里。** 全局的端点、Reader 的标记与自动清理、还有
   **手上这一本书**的目录。于是从 Context 那一侧点「设置」，「目录」整块消失而「标记」
   还在——同一个按钮在不同页面给出不同的表，读者无从判断哪些是全局的。
4. **两个入口。** 外壳左下角一个，阅读页顶栏又一个，同一张表。

第 1 条和第 2 条是同一个 bug 的两面：**设置页的清单和真正接线的清单是两份手写的东西**，
它们必然分头漂。

## 决策 1：能力表就是设置页的清单，判据是「配了就真的生效」

`CAPABILITIES` 从一个手写数组升级成**唯一的那一份**，`Capability` 由它派生，设置页
直接遍历它。清单与接线不再是两个地方。

进这份表的门槛只有一条：**配了就真的生效**。按这条，`embedding` 和 `claim` 出局——
它们是「点了不生效、也不报错」的旋钮，而这种坏法一点声音都没有。

> **加回来的条件是「接线的同时加」，不是「先留个位」。**
> 留位的那一版已经证明了它会一直留着：`embedding` 那行注释写着「这里先留位」，
> 而它在那儿待到了这次。

`parseConfig` 一并**丢掉不认识的能力**。退休一个能力时，旧 `config.json` 里残留的那一段
必须一起走——留着它，下次谁打开这个文件都会以为那一段还管用。

## 决策 2：能力按任务切，不按产品切；设置页按「谁在用」标注，不按产品分栏

ADR-0010 早就定了「每个功能各配各的端点」。这次要回答的是它的推论：Writer 的写作助手
和 Reader 的问文档，是**同一个能力还是两个**？

**两个。** 问文档是单文档问答、材料是这一篇 PDF 的原文（`pdfstudio/CONTEXT.md`）；
写作助手的材料是正在写的稿子加从知识库召回的 context。两件事对模型的要求不一样，
共用一个能力就意味着调其中一个必然动到另一个。所以多一个 `writing`。

但**它们仍然配在同一页上**，只在每个能力旁边标出「谁在用」。按产品分栏（Reader 一栏
端点、Writer 一栏端点）看着更整齐，代价是「同一个端点、写作换个更大的模型」这种最常见
的配法要把地址和 key 再抄一遍——那正是 ADR-0010 当初否掉「按组回退」的同一个理由。

**所以「三侧的设置不互通」的修法不是把三份合并，是承认它们本来就是一份。**

## 决策 3：设置是外壳里的第四个根，不是盖在内容上的一层

跟 ADR-0003 决策 3 同一个口径：Reader、Context、Writer、每一本书、每一篇稿子都平级，
没有「模式」这一层。设置此前是个原生 `<dialog>` 覆盖层，那让它在结构上比别的都特殊，
而它并不特殊——它有自己的子页和自己的历史。

归属表落在 `pdfstudio/src/app/settings-map.ts`，带测试。它守着一条硬约束：

> **一块设置可以不出现，但绝不允许出现在两页上。**

出现两次的那一刻，两处就会开始各自漂移——那正是这次要修的毛病。

四页：

| 页 | 有什么 | 为什么在这儿 |
|---|---|---|
| **模型** | 默认组、本地识别引擎、每个能力的覆盖 | **三侧共用的那一份。** 能力按任务切，与产品无关 |
| **Reader** | 标记改名、自动清理、这本书的目录 | 只作用于摘录。目录连一侧都不属于——它属于手上这一本书 |
| **Context** | （空，照直说） | 库跟着应用数据目录走；聚类是算出来的，不是调出来的 |
| **Writer** | （空，照直说） | 写作助手用哪个模型在「模型」页配——那是个能力，不是 Writer 的私产 |

**空页面要说出为什么。** 空页面比错页面好，但沉默的空页面不行——读者会以为是没加载
出来，然后反复点它。所以 `PageSpec` 上有一个 `empty` 字段，测试守着「没有块的页必须
有这一句」。

## 决策 4：设置记着自己是从哪一样打开的

`Active` 多一个分支：`{ kind: "settings"; from: Settled }`。

`<dialog>` 时代，「关掉就回到刚才那一页」是浏览器白送的。做成根之后这一条得自己拿住：
读了一半去改个模型，回来必须还在那本书上——掉回书架的话读者要重新点开它，而**换书是
要重读 PDF、摘录和目录的**（ADR-0003 代价 1）。

`from` 的类型排掉了设置自己：**设置里不能再套一个设置**。侧栏那个按钮一直在，包括已经
站在设置页上的时候；不排掉的话点两次就再也退不回那本书，而且退出去看起来还挺正常
（退到了设置页）。这与 ADR-0003 删掉 `side × reading` 那个不可能组合是同一手。

**来路没了，设置跟着关。** 设置页开着的时候侧栏那一列还在，人可以把自己刚才在读的那本
从案头拿走。另一条路（留在设置里、把来路换成接班的那一项）代价更大：换书要重读 PDF、
摘录和目录（ADR-0003 代价 1），而那一下会在人盯着设置页的时候悄悄发生。

## 为什么不给每一侧各留一份配置文件

那才是真的「不互通」。三侧共用同一台机器、同一个读者、多半同一个 API key——分三份的
后果是换个 key 要改三个地方，而漏掉一个的表现是「某一侧突然不工作了」，且不报错。

## 代价

1. **`embedding` 和 `claim` 从配置里消失。** 曾经在 `config.json` 里写过它们的读者，
   那两段会在下一次保存时被丢掉。这是有意的（决策 1），但它确实是一次静默的数据删除
   ——被删的东西从来没生效过，所以行为上什么都不会变。
2. **设置不再是覆盖层，Esc 关闭和焦点陷阱要自己想。** 原生 `<dialog>` 白送的那几样
   没了。换来的是它和别的页面同构——有自己的子页、能被直接指过去。
3. **Writer 和 Context 两页现在是空的。** 结构留好了，等它们真的长出可配的东西直接进
   同一列。按决策 1 的门槛，那些东西要**接线的同时**才进来。
4. **`settings-map.ts` 是一份要维护的表。** 加一块设置要同时改表和组件。这是故意的：
   表上那条「一块只归一页」的约束，只有在表存在时才守得住。
