# ADR-0003：主题由 AI 提议，但先对齐已有的池

## 状态

Accepted（2026-08-17）

## 决策

入库时，AI 读这条材料给出 **1–2 个**候选主题；每个候选先到已有主题池里找同义的，
找到就改用读者已经在用的那个词；读者确认或改写。主题可以留空——那就是孤儿。

**不把整个主题池摊给读者挑。**

## 为什么不是显而易见的那个（补全）

「输入时列出已有主题供选」是所有人的第一反应，它确实能治好同义词。但它会造出另一种毛病。

`public/knowledge-topics-prototype.html` 量过四种规则。做法是给每条材料一个隐藏的
**真值概念**，于是漂移变成两个可算的数：**漏边**（讲同一件事却没连上）、
**假边**（不相干却连上了）。

| 规则 | 漏边 | 假边 |
|---|---|---|
| 自由填 | 3 | 0 |
| 带补全 | 0 | **6** |
| AI 提议，不看池 | 4 | 0 |
| **AI 提议 + 看池** | **0** | **0** |

**两种失败的成因和药方完全不同**：漏边来自同义词，药方是让读者看见已有的池；
假边来自笼统主题，而**补全恰恰加剧它**——池子摊在眼前，人会顺手点一个勉强沾边的，
于是四条毫不相干的材料连出 6 条假边。

所以提议要**窄**：只给这条材料真正读出来的一两个候选，不摊开池子。
窄提议同时拿到了池子的对齐效果和「不诱惑偷懒」。

## 一致 ≠ 对齐

AI 提议的价值常被说成「一致」——它不会像人一样两周后换个词。但一致救不了分叉：
读者自己先用「评测」写了两条，AI 之后一直提议 `eval`，两半各自整齐、中间断开，
丢掉 4 条边。**一致性来自 AI，对齐来自池子，两个都要**——这就是要多一步「看池」的理由。

## 代价

**假边仍然没有药。** 这条决策只解决漏边。读者执意每条都打 `agent-design`，规则拦不住。
线索是**主题稀有度**——一个什么都挂的主题信息量趋近于零，同一个量既能给聚焦视图排序，
也能在入库时提醒。等 `.scratch/knowledge-graph/issues/05` 定下排序规则再回头合并这两件事。

**主题改名是一次批量写。** 主题是自由词、内联存在每条 context 里，没有注册表，
所以合并或改名会改写所有引用它的 context。不可能像 PDF Studio 的标记那样
（名字住在书架根，摘录只存 id）改名只动一个文件。原型证明事后合并能把漏边归零，
但要按批量写来实现。

## 边界

**归一化仍然只做 `trim().toLowerCase()`**（`contextstudio/src/graph.ts`）。同义词的判断
留在入库口，不下沉进 `buildGraph`——那个函数必须是纯规则，掺进判断就再也说不清
「这条边为什么在」。
