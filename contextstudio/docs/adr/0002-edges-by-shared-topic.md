# ADR-0002：边是共享主题的 context 两两相连

## 状态

Accepted（2026-08-17）

## 决策

两条 context 只要至少共享一个**主题**，它们之间就有一条边。主题本身**不是节点**——
图上只有 context。

边记住它共享的是哪几个主题：`{ a, b, topics: string[] }`。

## 考虑过的另一种画法

把主题也做成一类节点，context 只连到主题节点（Obsidian 处理 tag 的方式）。那样边数是
O(n)，图稀疏可读，热门主题自然收成一个枢纽。

**没有选它。** 选择是明确做出的，不是默认落到这里的：主题节点会在图上引入第二种本体——
读者盯着一个圆点得先分辨「这是一条断言还是一个词」。知识图想表达的是「这两条材料互相
有关」，主题只是**判定有关的依据**，不是图想展示的东西。把依据画成实体，就把一句方法论
提升成了领域概念。

## 代价

**边数是 O(n²)，而且是按主题分块爆炸的。** 一个主题下 n 条 context 就是 n(n-1)/2 条边：
100 条 → 4950 条边。一个热门主题足以把整张图糊成一团。

量过了（`public/knowledge-graph-prototype.html` 跑同一套规则，主题分布仿真实读法）：

| context 数 | 边数 | 图密度 | 最大度数 |
|---|---|---|---|
| 60 | 608 | 34.4% | 43 |
| 320 | 14,191 | 27.8% | 212 |

**密度不随规模下降**，稳定在 20–30%——因为每条 context 只从一个不大的主题池里挑 1–3 个。
320 条时最大度数 212、可能邻居总共 319，那已经接近完全图。

这个代价是**接受**的，不是被忽略的。缓解手段留给渲染层，不改数据模型：

- 聚焦是主视图（ADR-0001 已经因为节点粒度得出同一结论），全局图只在库还小的时候有意义
- 真的撑不住时，先加**主题的度数上限**（超过 N 条的主题在图上不产生边，但仍可筛选），
  而不是回头改成主题节点

如果有一天缓解手段全用尽还是不行，那时推翻这条 ADR，而不是现在提前设计。

## 边界

**图是给人看的导航，不是给 agent 的检索通道。**

`docs/workflow.md` §4 已经定过：「检索时不按 tag 查。纯 tag 匹配在库大了以后召回率差，
tag 体系还会漂移。应该拿当前 section 的标题 + 写作意图做语义召回，tag 只做硬过滤。」

这条 ADR 不推翻它。共享主题的边回答的是「读者点开这条，旁边还有什么」——一个导航问题。
生成阶段要的 context 仍然走语义召回，主题只做硬过滤。**任何拿这些边做召回的实现都违反
本条**，请回头改召回，别改这张图。

## 不进图的东西

PDF Studio 的**标记**（`TagColor` 五色闭集：要点/读懂了/术语/存疑/待查）**不产生边**。

它是阅读态——「我当时怎么处理这段」，不是内容——「这段讲什么」。跨 PDF 复用时前者没有
意义：「存疑」在这篇论文和那篇论文之间不构成关联。而且它只有五个值，按它连边等于把全库
塌成五个巨型连通块，信息量 log₂5。
