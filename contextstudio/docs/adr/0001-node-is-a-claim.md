# ADR-0001：节点是一条断言，不是一篇文档

## 状态

Accepted（2026-08-17）

## 决策

知识图的节点是**一条 context**——一个断言加它逐字的证据——而**不是**一篇笔记、一个页面
或一份文档。Obsidian 的节点是一篇 note，我们的不是。

## 为什么

因为读者不是人，是 agent。

传统笔记的读者是未来的自己：允许省略、允许私人缩写、允许「看到就想起来」。agent 没有
「想起来」这回事——你塞给它的那一条就是它拥有的全部，上下文不会跟着来。判据因此从
「我找得到吗」变成两条硬的：**塞得进**（prompt 预算有限，粒度必须均匀）和**信得过**
（每条能被单独核验）。

一篇文档两条都不满足：长度不可控，且内部混着五个论点、两个反例和一段跑题，无法整体
approve 也无法整体引用。

这不是新发明，是把仓库里已有的两句话推到底：`docs/workflow.md` §2.1 说「存的不是『这条
资料相关』，而是『它能支撑哪一句断言』」；§1.5 说每个断言要么有 provenance 要么标记
authored。provenance 指向的东西必须与断言同粒度，否则「这句话的出处」永远只能指到一整篇。

## 代价

**图会很碎，而且很密。** 一本论文读下来几百个节点，不是几十个。这直接决定了：

1. **全局图不是主视图。** 断言粒度下的全景必然是一团毛线。聚焦（某节点 + 邻居）才是常态。
2. **入库时的拆分质量决定一切。** 一条 context 塞了三个断言，它在图上就是一个假节点——
   连出去的边有一半不成立。所以「能不能被单独 approve 或 reject」这条判据要卡在入库口，
   不能留到图上再补救。

## 边界

**不给节点定存储格式。** ADR-0011（PDF Studio）明确把知识库的存储留白，这里继续留白——
等 `ContextStore` 真要落盘时再定，那时才有真实约束可依。
