# ADR-0003：发布 = 往一个 git 去处提交一次翻译过的文章

## 状态

Accepted（2026-08-27），**同日被 ADR-0004 收窄**：决策 1「用 git 不用 scp」讲的是
「稿子 → 本地博客仓库」那一段，仍然成立；但**「去处」这个词已经不再指那个仓库**。
见 `0004-destination-is-a-cloud-site.md`。

## 背景

稿子写完之后要送到别处去——一个静态博客。最初的想法是 `ssh` / `scp`：把 `.md` 拷到
服务器的某个目录。附件是提出 git 的理由（「一篇文章可能还带几张图」），但那不是最硬的
那条理由。

## 决策 1：用 git，不用 scp

真正的理由是 **update 这个词**。

`scp` 是一次没有记忆的覆盖。第二次推上去时，你没有任何办法知道那边那份是不是你上次推的、
中间有没有人动过——它不会告诉你，它只会盖。git 给的是同一路径的幂等更新、一份历史、
以及**冲突会被发现**（推不上去就是对面先走了一步，那是要人看一眼的事）。附件只是顺带。

还有一条更硬的：scp 要一把能写你服务器的钥匙，而 `config.json` 里已经躺着模型的 apiKey
了（`pdfstudio/docs/adr/0005`）。git 走系统里已经配好的凭据，**我们一个字节的凭证都不存**。

代价：去处必须是一个**本地已经 clone 好的工作副本**，不是一个远程地址。换台机器要先自己
clone。选它是因为博客本来就在手边，而「我们自己维护一份 clone」要多一整套 clone / fetch /
冲突恢复的错路，换来的只是省掉一次 `git clone`。

## 决策 2：发布是翻译，不是拷贝

|  | 稿子 | 文章 |
|---|---|---|
| 标题 | 正文第一行，派生的（`draft.ts`） | frontmatter 里的字段，正文里不再留一份 |
| 出处 | 正文里写着 `[ctx:xxx]` / `[authored]`（ADR-0002） | 文末的脚注 |
| frontmatter | JSON，只有 id 和时间 | YAML，title / date / draft / 那边自己的字段 |

最后一行是会出事的那一行：**原样推上去，`[ctx:a3f1]` 会出现在公网页面上。**

`[ctx:]` 转成 Hugo 自带的脚注语法（`[^1]`），不自己拼一节「参考」——脚注带回跳锚点，
读者点一下能回到引用它的那句话。**引了但库里没有的 id 既不删也不渲染**：删掉等于把一句
没出处的话送上公网，渲染等于**编**一条参考。它原样留着，并且单独报出来。

## 决策 3：更新时，那边手写过的字段一个都不动

`categories`、`tags`、`cover` 是人在博客那侧加的，稿子这边根本没有对应的东西。生成一份
新 frontmatter 盖上去，等于每次发布都清一次——而且清得悄无声息。

所以只按行改 `title` 那一行，别的原样留着；**`date` 也不动**（那是文章面世的日子，不是这次
改动的时间，每次发布都推到今天的话，首页顺序会跟着每一次错别字修订翻一遍）。

不引 YAML 库同样不是为了省依赖：解析再序列化会顺手把注释、引号风格、键的顺序全部重排，
git diff 上就是整块 frontmatter 都变了——而那正是「我到底改了什么」最需要看清楚的地方。

## 决策 4：发过一次就认那条路径

标题是稿子的派生物，改一个字它就变。跟着重算地址的话，改标题等于在公网上又发一篇，
而旧的那篇还挂在原地——**两篇都在，没人告诉你**。所以落点记进账本，之后都走它。

账本（`published.json`）与去处配置（`destinations.json`）**分成两份文件**：后者是你手写的，
我们只读、一个字都不回写。合成一份的话，每记一次发布就要重写一遍你手写的那份——Loop 的
开关为同一个理由单独用一个标记文件，不碰 `loop.md`。

## 决策 5：计划与动手是两次请求

按下去就是往你的博客仓库提交并推送，多半等于文章当场公开。所以先出一份计划（写哪个文件、
新建还是覆盖、frontmatter 长什么样、那边现在是什么），确认了才动手。

`docs/workflow.md` §⑦ 说「确定性检查全绿才能 merge」，这里照办：`blocked` 拦住，
**`marked` 不拦**——值得看一眼不等于不能发，那一档要是也拦，人会开始学着忽略它。

提交只带我们写的那几条路径（`git commit -- <路径>`）：**你的博客就是你自己的仓库**，
里面有你正在改的别的东西是常态，把它们一起卷进一个「发布」提交里，是这类工具最容易犯、
也最难收拾的错。绝不 force push。
