# ADR-0005：一个目录、两个状态，「稿子」退休

## 状态

Accepted（2026-08-27）

## 背景

数一下就清楚了：

- 仓库里 **92 篇**文章，Blog Studio **一篇都看不见**
- 「未完成」有**两套互不知道的**：仓库里 26 篇 `draft: true`，Blog Studio 自己 2 篇稿子
- 身份也有两套：稿子是 uuid，文章是 slug

三处重复，每一处都会各自漂。

## 决策 1：统一目录

`<repo>/site/content/blog/` 是唯一的地方。Blog Studio 的 `drafts/` 退休，那 2 篇搬进来。

**文件仍然是唯一真相**（`pdfstudio/docs/adr/0011` 的形状）：把一个 `.md` 丢进那个目录就能
打开，不用导入；拿别的编辑器改也不会坏。

## 决策 2：「稿子」这个词退休

一篇**文章**有两个状态，**用 Hugo 自带的标记，不发明第二套**：

- **在架** `draft: false` —— 会被构建，出现在网站上
- **下架** `draft: true` —— 不构建，同步时从云端消失，**文件原地不动**

已实测：`draft: true` 的文章确实不进构建产物。所以「下架」不需要任何新机制。

「稿子」原来指「还没发出去的东西」——那现在只是**下架**这个状态，不值得一个名词。

## 决策 3：id = slug = 文件名

一路上少一次转换，也少一本账：`published.json` 里那半本「哪篇落在哪条路径」不再需要，
因为路径由 slug 直接算出来。

代价：改标题不会自动改地址。**这正是要的**——改地址等于在公网上又发一篇，
而旧的那篇还挂在原地（ADR-0003 决策 4 说的就是这件事，现在它变成了结构上的事实）。

## 决策 4：删除是移进回收站

`<repo>/.trash/<时间戳>-<slug>.md`。时间戳前缀不是装饰：**同一个 slug 删两次，
不能后一次盖掉前一次**。

`.trash/` 比 `git revert` 好用的地方在于**你能直接看见里面有什么**，不用回想是哪个 commit。

## 决策 5：不留版本

文章不留 revision。`revisions.ts` 那套（线性追加、取回旧版）是给 `docs/workflow.md`
设想的 agent 自动改稿准备的——**人自己写文章不需要它**，而每一版都留会让统一目录里
多出一堆没人看的东西。

要找回改动就去 `.trash/`，或者你自己的 git（如果你 commit 了）。

## 决策 6：本地一个索引，云端没有

SQLite 只当索引。**判据：删掉那个 `.db`，不该有任何东西找不回来。**

云端不放数据库，决定性的理由是：**`deploy.sh` 还在，你还会用它**——那个脚本一跑，
任何我们放在服务器上的状态文件立刻就是错的，而且不报错。云端的真相就是那个目录。

## 后果

- `draft-store.ts` 在博客这一侧被 `article-store.ts` 取代（JSON frontmatter → YAML）
- 标题的规则变了：**先看 frontmatter 的 `title`**，没有再退回正文第一个标题行——
  那 92 篇的正文里多半没有 H1，因为 Hugo 自己渲染标题
- **Writer 的自动保存从此写进你的 git 仓库工作区**，写作时 `git status` 会一直是脏的。
  这是明知的代价：换来的是没有第二个目录、没有第二套「未完成」
