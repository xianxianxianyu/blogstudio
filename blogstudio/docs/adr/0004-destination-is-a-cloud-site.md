# ADR-0004：去处是一个云端站点，本地仓库降级成中转站

## 状态

Accepted（2026-08-27）

## 背景

ADR-0003 把「去处」定义成**本地一份 git 工作副本**：稿子翻译成文章、提交、push，
就算发布完了。

接上真实基建之后这个定义站不住：`scripts/deploy.sh` 一句话说明了上线是怎么回事——

```
hugo --minify --cleanDestinationDir
rsync -avz --delete -e "ssh -p 2222" public/ root@45.143.235.215:/srv/blog/
```

**push 到 GitHub 不会让任何人看到那篇文章。** 真正让它出现在网上的是构建加同步。
而且现在有两个域名要发（`moyutianzun.com` 在日本 VPS，`moyutianzun.cn` 在阿里云），
它们共用同一份内容、同一套 UI。

## 决策 1：去处 = 一个云端站点

`{ name, host, path, baseURL }`。`host` 是 `~/.ssh/config` 里的别名——**不写 IP、端口、
用户名、密钥路径**：那些已经在 ssh config 里了，抄一份就会漂，而且这样依旧一个字节的
凭证都不存（ADR-0003 决策 1 的理由原封不动地继承下来）。

本地那份博客仓库**降级成固定的中转站**，从配置里的一个可选项变成 `Config.repo` 一个字段。
ADR-0003 的翻译与提交那一套全部保留，只是它不再是终点，而是四段里的前两段。

## 决策 2：一篇文章的发布，是整站重建

静态站没有「只上传一篇」这回事：加一篇会改首页、分类页、标签页、RSS、sitemap。
所以「送一篇过去」= 写文件 → 提交 → **整站构建** → 整站同步。

界面上必须写着这句话。人第一次看到「新增 18 个文件」会以为出错了，而那正是对的。

## 决策 3：差异问 rsync 自己要

干跑一次 `--dry-run --itemize-changes`，解析它的原话，而不是自己比对两边的文件表。
我们的算法跟它不一致的那一刻，屏幕上说的和磁盘上发生的就是两回事——而这件事里有一半
是**删除**。

三个参数一个都不能少，全是实测逼出来的：

- **`-8`**：不加的话中文文件名被转义成 `\#226\#234\#232`，而这个博客的文件名就是中文的。
  与 `git-repo.ts` 里的 `core.quotePath=false` 是同一处伤疤。
- **`-c`**：不加的话 rsync 判「变没变」看大小和时间，而 Hugo 每次全量重建都会刷新所有
  mtime——于是每次部署都显示「几百个文件改动」，人看两次就不看了。
- **`--delete`**：本地删掉的文章要在云端消失。它是这一整件事里唯一不可逆的部分，
  所以删除清单单独显示、单独计数。

另外两个坑也是实测才知道的：`*deleting` 每条会打两遍；删一整个目录时目录自己和它里面
每个文件各来一条。两条都在 `rsync-plan.ts` 里收干净了。

## 决策 4：同步前 probe，不像站点就拒绝

`--delete` 指错目录会清空它。所以动手前查一次：目录在不在、里面有没有 `index.html`。
不满足就抛，并且**在 `sync` 里查，不是在计划里查**——计划是几秒钟前那一刻的照片。

## 决策 5：一个去处一个 baseURL、一个产物目录

共用 `site/public/` 的话，后同步的那个会带着前一个的绝对链接：`.cn` 的 RSS、sitemap、
canonical 全指向 `.com`，**而页面看起来完全正常**，没有任何地方会报错。

产物目录名由去处的名字派生，而那个名字是人手写的——所以要先过 `slugOf`：它紧接着交给
`--cleanDestinationDir`，那个参数会**清空**它指向的目录，一个写成 `../..` 的名字就是在
删别处的东西。

## 决策 6：图片进仓库，但 `.cn` 由服务器弹回 OSS

那 92 篇里有 238 处图片引用，全是硬编码的绝对地址，指向广州的一个阿里云 OSS 桶。
三个毛病：**它是单点**（桶没了两个站的图同时全死）、**它是唯一一处内容不在仓库里的东西**、
海外读者从广州拉图。

所以把 231 张（62 MB）拉进 `site/static/images/`，正文里改成相对路径 `/images/x.png`。
图片从此跟文章走同一条路：改本地 → 构建 → 同步，管道一个字没改（Hugo 把 `static/`
原样拷进产物）。

**但 `.cn` 不传图片。** 那台阿里云出网实测只有 **3.3 Mbps**——一页五张图约 1.3 MB，
从它那儿发要三秒多，还是单人。这正是当初图片放 OSS 的原因。

解法是**不让内容分叉**：两个站的 HTML 逐字节相同，都写 `/images/x.png`；
去处配置上给 `.cn` 一个 `exclude: ["images/"]`（那 62 MB 根本不往细带宽的机器上传，
而且被排除的路径也不会被 `--delete` 删掉），再由 OpenResty 一条跳转把 `/images/`
指回 OSS。**变的只是「谁来发这些字节」，不是内容。**

用 **302 不用 301**：永久跳转会被浏览器缓存住，哪天想改回本地发就收不回来了。

## 决策 7：图片先落本地，发布时**针对性**上传

Writer 里粘一张图 → 存进 `site/static/images/`，正文写 `/images/x.png`。
**名字由内容决定**（sha256 前 16 位）：同一张截图粘进两篇文章只存一份。

（在此之前这条路根本没接：Crepe 的默认 `onUpload` 返回 `URL.createObjectURL(file)`，
也就是一个 `blob:` URL——**关窗即死，而且会存进文章文件、跟着同步上公网**。）

发布时**图片和正文各走各的路**，由去处声明：

- 没写 `images` = 图跟着 rsync 走（`moyutianzun.com`）
- 写了 `images: "oss://桶/前缀/"` = 传 OSS，正文那边配 `exclude: ["images/"]`（`moyutianzun.cn`）
  配置校验会拦住只写一半的情况——那 62 MB 会照传一遍然后没人用。

**「针对性」有两层**：只传这次会上线的文章用到的图（从索引的 `uses` 表算），
而且只传**那边没有的**那几张（`ossutil ls` 问出来，不猜）。

**只增不删。** 跟正文那侧的 `--delete` 故意不对称：OSS 上那 231 张是 `.cn` 唯一的图源，
某篇临时下架就把图删掉等于把线上页面弄坏。清理孤儿是单独的、人按下去的动作
（`index.orphans` 只报不删）。

**图片先传，正文后同步。** 反过来的话，中间那段时间页面上是一排破图；
这个顺序有测试钉着。

凭证归 `ossutil` 管（`~/.ossutilconfig`），**我们一个字节都不存**——跟 ssh 那条完全同形。

## 没有解决的

`.com` 与 `.cn` 内容完全一样，是两份重复内容。让 `.cn` 的 canonical 指向 `.com` 需要
fork PaperMod 的 `head.html`（190 行，canonical 在第 25 行，而它的扩展点在第 186 行，
从那儿再输出一个就是两个打架的标签）。**一行的收益、190 行的漂移面**，暂时不做，
见 `.scratch/blog-deploy/issues/04`。
